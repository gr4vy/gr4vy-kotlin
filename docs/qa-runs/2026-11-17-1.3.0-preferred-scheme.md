## Server probe

`scripts/qa/probe-versioning.sh` with a Visa card that has no co-badged scheme:

| Query | Status | Meaning |
|---|---|---|
| none | 200 | baseline, visa DS |
| `preferred_scheme=visa` / `=mastercard` / `=foo` | 200 | parameter ignored |
| `preferredScheme=visa` / `=mastercard` | 200 | read; mastercard isn't one of the card's schemes, so it falls back to visa |
| `preferredScheme=foo` | 400 | read and validated against the scheme enum |
| `preferredScheme=cartes-bancaires` | 400 | the enum value is `carte-bancaire` |

Two contract issues follow from this:

1. **Parameter name.** The SDK sends `preferred_scheme` and the server reads `preferredScheme`. The tickets (TA-19227, TA-19229, TA-19230) still say `preferred_scheme`, so they need correcting too.
2. **Invalid values aren't a fallback.** The ticket says an invalid scheme falls back to the card's primary scheme. The server only falls back for a *valid* scheme that the card doesn't carry. An unknown value is a 400, which the SDK turns into `attempted: false`, so 3DS is silently skipped. The README and KDoc use `cartes-bancaires` as the example. That is one of those unknown values: the scheme value is `carte-bancaire`.

With the co-badged sandbox card `4035501000000008` (Visa, with Cartes Bancaires as an additional scheme), in GBP, where the cardholder picks Cartes Bancaires:

| Query | Status | Meaning |
|---|---|---|
| none | 200, Visa DS | baseline |
| `preferred_scheme=carte-bancaire` (what the SDK sends) | 200, **Visa DS** | 3DS runs on the brand the cardholder didn't pick |
| `preferredScheme=carte-bancaire` | 204 | correct: Cartes Bancaires has no 3DS configuration on spider, so the SDK reports `attempted: false` |
| `preferredScheme=visa` | 200, Visa DS | correct |
